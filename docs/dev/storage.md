# Storage and uploads

Career Assistant stores document bytes through the family object-storage
contract. The deployment backend is configuration, not a code path:
**desktop is always local**, web defaults to the mounted uploads volume, and
an AWS/Azure/cloud profile uses `s3` or `azure_blob` only.

Contract (vendored byte-identically from the family object-storage contract):

- `backend/app/storage/object_storage.py`
- `backend/tests/fixtures/object_storage.fixtures.json`

Re-sync with the family contract sync tool; never edit the vendored copy.
The per-upload limit is `Settings.max_upload_mb` (25 MB) and stays enforced
by the upload service. Leave `CAREER_OBJECT_STORAGE_MAX_MB` unset: the
contract's per-object cap binds to the **largest object class** on this host,
`max(max_upload_mb, export_max_mb)` — 1024 MB with the default export
ceiling — so a full data export can be written. (The generated table below
describes the generic host ceiling; this host widens the *store* cap while
upload authorization remains 25 MB.)

## Shape

`app/storage/bootstrap.py` resolves the configuration from `Settings`,
builds the store, probes it and registers it for the process. `app/main.py`
exposes it as `app.state.objects` (plus `app.state.document_storage`) and
closes it on shutdown. Request handlers reach the same store through
`app.services.profile.document_storage.document_storage()`.

`DocumentStorage` is the one seam between the `documents` rows and the
backend:

| Method | Meaning |
|---|---|
| `put_document(document, data)` | write the original upload, return its key |
| `read(document)` | bytes (object first, then the legacy local file) |
| `stream(document)` | chunked iterator (same dual-read) |
| `materialize(document)` | private `0600` temp file, removed on exit |
| `delete(document)` | remove the source object and every page object |
| `put_page` / `read_page` | derived CV page images |
| `put_export` / `stream_key` | user data-export archives |

Async callers use the `a*` variants (`aput_document`, `aread`, `astream`,
`adelete`, `amaterialize`); every one crosses `anyio.to_thread.run_sync`, so
provider latency never blocks the event loop. Synchronous callers (the
auth-kit user store, the desktop CLI) use the primitives directly.

The database stores `documents.object_key` — never a path. Rows written
before the contract keep `object_key` from the backfill and still read their
legacy `<upload_dir>/<id><ext>` file when the object is absent (dual-read);
the same fallback covers derived pages under
`<upload_dir>/derived/<id>/page-<n>.png`. A path-taking processor receives
a private `0600` temp copy of that legacy file, never the durable path.

At the HTTP edge contract failures are mapped, not leaked: `ObjectNotFound`
→ 404, `UnsupportedOperation` → 409, `ObjectTooLarge` → 413,
`StorageUnavailable`/`StorageAuthError` → 503, configuration/key errors →
500. A download prefetches its first chunk before the response starts, so a
row whose object vanished is a 404 rather than a broken stream.

## Keys

```
tenants/<user-id>/documents/<document-id><ext>
tenants/<user-id>/cv_pages/<document-id>-p<index>.png
tenants/<user-id>/exports/<job-id>.zip
```

Keys are server-generated by the contract builders; a user filename never
becomes a path (only its sanitized extension is used for type detection).
Deleting a document enumerates every object under the
`tenants/<user-id>/cv_pages/<document-id>-p` prefix — never the row's
`page_count`/`extraction`, which can still be empty during a failed or
in-flight run — and removes the source; an object shared by another row is
left in place (the async delete checks for a sharing row before removing
bytes). A legacy local file is read through a private `0600` temp copy when
a processor demands a path.

## Storage status card

Settings → Storage (admins only, Administration section) is a read-only
operator card, not a provider wizard. It shows the resolved backend,
bucket/container, key prefix, region and endpoint host, SSE mode, per-object
cap, presign TTL and the live health row. There is deliberately no credential
field, provider tile or backend switch: storage is deployment configuration,
and a switch is the migration tool, not a save button.

- API: `GET /api/v1/admin/storage/status` (admin-only; non-admins get 403).
  It reuses the cached, bounded `StorageHealthProbe` behind `/health`.
- `?refresh=true` drops the 30 s health cache first, so **Test connection**
  performs a real probe instead of repeating a snapshot.
- The response carries no credentials, connection strings, presigned URLs or
  full endpoint URL — only the endpoint host.
- The family `app.storage` settings-map domain (scope `instance (admin)`,
  secrets `none`) is declared in `contracts/settings-map.json`; the frontend
  conformance test pins this host's administration nav to that declaration.

## Configuration

All variables are prefixed `CAREER_`; nothing unprefixed is read. `.env` and
the process environment both populate the host settings, and the storage
bootstrap maps the resolved values into the contract — application code
never reads the raw environment.

| Variable | Values | Default |
|---|---|---|
| `CAREER_CLOUD_PROFILE` | `aws` / `azure` / `gcp` / `cloud` / empty / `none` / `local` / `self_hosted` | empty (the last three mean "no profile") |
| `CAREER_OBJECT_STORAGE_BACKEND` | `local` / `s3` / `azure_blob` | profile default, else `local` |
| `CAREER_OBJECT_STORAGE_REQUIRED` | bool | `true` with a cloud profile |
| `CAREER_OBJECT_STORAGE_LOCAL_ROOT` | path | host data directory |
| `CAREER_OBJECT_STORAGE_MAX_MB` | 1–1024 | `25` (host ceiling) |
| `CAREER_OBJECT_STORAGE_PRESIGN_TTL` | 60–3600 | 300 |
| `CAREER_S3_BUCKET` / `_REGION` / `_ENDPOINT_URL` | provider config | — / SDK default / AWS |
| `CAREER_S3_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY` / `_SESSION_TOKEN` | static credentials (all or none) | SDK chain |
| `CAREER_S3_PATH_STYLE` / `_KMS_KEY_ID` / `_PREFIX` | provider config | path-style when an endpoint is set / AWS-managed key / empty |
| `CAREER_S3_SSE` | `AES256` / `aws:kms` / `none` | `AES256` for cloud/AWS; `none` for a custom endpoint outside a cloud profile |
| `CAREER_S3_VERIFY_TLS` / `_CONNECT_TIMEOUT` / `_READ_TIMEOUT` / `_MAX_ATTEMPTS` | transport | `true` / 5 / 30 / 3 |
| `CAREER_AZURE_STORAGE_CONTAINER` / `_CONNECTION_STRING` / `_ACCOUNT_URL` / `_ACCOUNT_NAME` | provider config | — |
| `CAREER_AZURE_STORAGE_CREDENTIAL` | account key, SAS, or `managed_identity` | SDK default |
| `CAREER_AZURE_STORAGE_PREFIX` | object key prefix | empty |
| `CAREER_AZURE_CONNECT_TIMEOUT` / `_READ_TIMEOUT` / `_MAX_ATTEMPTS` | transport | 5 / 30 / 3 |

Resolution law:

- **Desktop is always local.** A desktop entrypoint with a cloud profile,
  `s3` or `azure_blob` is a boot error: there is no bucket, SDK or storage
  configuration on the desktop.
- **Cloud never runs local.** A server entrypoint with `aws`, `azure`,
  `gcp` or `cloud` never resolves to `local`; requesting `local` under any
  cloud profile is a boot error.
- **Server defaults to local.** With no profile and no requested backend,
  a server boots on the mounted local volume. `s3` / `azure_blob` is
  selected explicitly; an `azure` profile may select `s3` for an
  S3-compatible gateway.
- **Required forbids local.** `CAREER_OBJECT_STORAGE_REQUIRED=true` rejects
  `local` even without a cloud profile, and a cloud profile implies
  required.

The app builds and health-probes the store before it starts serving.
`probe=True` performs a cheap write/unlink under a local root,
`HeadBucket` for S3 and container properties for Azure, so a bad bucket,
container, credential or non-TLS cloud endpoint fails boot instead of the
first upload. The only sanctioned `probe=False` boot is the documented
read-only rollback window in the migration runbook.

**Upload ceiling.** Leave `CAREER_OBJECT_STORAGE_MAX_MB` unset unless the
deployment intentionally lowers the cap. `Career Assistant` binds unset to its
`25` MB host upload ceiling; the contract default is **100**
for hosts that do not bind one. Never pin 100 in compose to "match the
default" — an empty value is what binds the host ceiling.

## Transfer and security

**Uploads are server-mediated.** The host authenticates and authorizes
the caller, reads the body under `CAREER_OBJECT_STORAGE_MAX_MB`, validates
the content type and extension, sniffs the bytes, then calls
`store.put(key, data, content_type=..., metadata=...)` and persists the
key (never a path). The contract refuses presigned **PUT**: a browser
writing directly to the bucket bypasses authorization, the byte cap and
the audit trail. Do not add one later.

**Downloads have two legal shapes.** Use `store.stream(key)` through an
authenticated route (local, or a cloud backend where presigning is
unavailable), or `store.presign_get(key, ttl, download_filename=...,
inline=False)` which redirects to the provider for a short TTL.

- **GET-only presigning.** Presigned URLs are for reads; there is no
  presigned write.
- **TTL 60–3600 seconds.** The default is 300. Re-check authorization
  when the URL is minted; never log or store the URL.
- **`attachment` + `no-store` by default.** A presigned response carries
  `Content-Disposition: attachment` and `Cache-Control: no-store`.
- **Inline is an explicit image-only opt-in.** Set `inline=True` only for
  the image MIME types the host allows; never for HTML, SVG or XML.
- **`nosniff` always.** Streaming and redirected responses both carry
  `X-Content-Type-Options: nosniff`.
- **A vanished object is a 404.** A database row whose object is gone
  returns 404 when the stream opens; the ownership check still runs first.
- **Azure identity limits presigning.** A managed identity cannot sign a
  SAS; a SAS credential can access but not presign. In both cases the
  contract raises `UnsupportedOperation` and the host streams through the
  app instead of minting a broken URL.

## Cloud deployment checklist

Prerequisites:

- a **private, TLS-only** bucket or container: no public access, no
  plaintext HTTP endpoint;
- a **prefix per product and environment** (`CAREER_S3_PREFIX` /
  `CAREER_AZURE_STORAGE_PREFIX`, for example `prod/`), so one bucket can
  serve staging and production without collisions;
- a **least-privilege identity**: an instance/task role or managed
  identity over static keys, with list and object verbs only on the
  deployment prefix.

Deploy from the repository root with the production and cloud overlays:

```bash
docker compose -f docker/docker-compose.prod.yml \
               -f docker/docker-compose.cloud.yml up -d
```

**Success** means the app boots, its storage health probe passes, and an
upload followed by a download works end to end. **Failure** is a boot
error, not a degraded start: a missing bucket/container, missing or
one-sided static credentials, a non-HTTPS cloud endpoint or `SSE=none`
under a cloud profile stops the process.

- **Leave the max-MB cap unset.** An unset
  `CAREER_OBJECT_STORAGE_MAX_MB` binds to `Career Assistant`'s
  `25` MB host ceiling; the contract default is 100 for hosts
  that do not set one. Pin a lower value only intentionally.
- **The web image ships both extras.** Install `object-storage-s3` and
  `object-storage-azure` in the web image; desktop packaging installs
  neither. One image can therefore boot an S3 or Azure deployment.
- **An empty bucket/container is ready.** A newly provisioned, empty
  target needs no migration.
- **Existing data needs migration.** Pointing a cloud profile at an
  existing local volume without the `migrate-objects` tool serves empty
  objects. Follow the migration runbook below.
- **Do not mount the uploads volume** in a cloud deployment: the
  container is stateless for object bytes. Provider durability and
  versioning cover them; the database backup sidecar does not copy
  objects.

## Provider examples

**AWS S3 — instance/task role (recommended)**

Prerequisites: a private, TLS-only bucket in the chosen region. Grant the
instance/task role `s3:ListBucket` on the bucket and
`s3:GetObject`/`s3:PutObject`/`s3:DeleteObject` on the deployment prefix.
With a customer-managed KMS key, also grant `kms:GenerateDataKey` and
`kms:Decrypt`.

```env
CAREER_CLOUD_PROFILE=aws
CAREER_OBJECT_STORAGE_BACKEND=s3
CAREER_S3_BUCKET=product-prod
CAREER_S3_REGION=eu-central-1
CAREER_S3_PREFIX=prod/
# CAREER_S3_SSE=aws:kms
# CAREER_S3_KMS_KEY_ID=arn:aws:kms:...
```

No static keys belong in env when the instance/task role supplies them.

**AWS S3 — static keys + KMS**

```env
CAREER_CLOUD_PROFILE=aws
CAREER_OBJECT_STORAGE_BACKEND=s3
CAREER_S3_BUCKET=product-prod
CAREER_S3_REGION=eu-central-1
CAREER_S3_ACCESS_KEY_ID=...
CAREER_S3_SECRET_ACCESS_KEY=...
CAREER_S3_SSE=aws:kms
CAREER_S3_KMS_KEY_ID=arn:aws:kms:...
CAREER_S3_PREFIX=prod/
```

Prefer the role over static keys; rotate them and never commit them.

**S3-compatible endpoint (MinIO/R2/B2/Wasabi/Ceph)**

Cloud profile — the contract requires SSE `AES256` or `aws:kms`:

```env
CAREER_CLOUD_PROFILE=cloud
CAREER_OBJECT_STORAGE_BACKEND=s3
CAREER_S3_BUCKET=product
CAREER_S3_ENDPOINT_URL=https://minio.example.com
CAREER_S3_PATH_STYLE=true
CAREER_S3_ACCESS_KEY_ID=...
CAREER_S3_SECRET_ACCESS_KEY=...
CAREER_S3_SSE=AES256
CAREER_S3_PREFIX=prod/
```

Gateway that rejects the AWS SSE header — run it as self-host object
storage instead of a cloud profile:

```env
CAREER_OBJECT_STORAGE_REQUIRED=true
CAREER_OBJECT_STORAGE_BACKEND=s3
CAREER_S3_BUCKET=product
CAREER_S3_ENDPOINT_URL=https://minio.example.com
CAREER_S3_PATH_STYLE=true
CAREER_S3_ACCESS_KEY_ID=...
CAREER_S3_SECRET_ACCESS_KEY=...
CAREER_S3_SSE=none
CAREER_S3_PREFIX=prod/
```

Outside a cloud profile, a custom endpoint defaults to `SSE=none`; many
S3-compatible gateways reject the AWS SSE header. Set `AES256` only when
the gateway supports it. A cloud profile always requires
`AES256`/`aws:kms`.

**Azure Blob — managed identity (recommended)**

Prerequisites: the container exists and is private/TLS-only. The identity
needs **Storage Blob Data Contributor** on the container (or account).
`azure-identity` is in the web image. This contract presigns only with an
account key; a managed identity therefore streams downloads through the
app.

```env
CAREER_CLOUD_PROFILE=azure
CAREER_OBJECT_STORAGE_BACKEND=azure_blob
CAREER_AZURE_STORAGE_CONTAINER=product-data
CAREER_AZURE_STORAGE_ACCOUNT_URL=https://product.blob.core.windows.net
CAREER_AZURE_STORAGE_ACCOUNT_NAME=product
CAREER_AZURE_STORAGE_CREDENTIAL=managed_identity
CAREER_AZURE_STORAGE_PREFIX=prod/
```

Do not put a raw expiring token in env; the `managed_identity` sentinel
selects `DefaultAzureCredential` (managed or workload identity).

**Azure Blob — connection string or account key**

Connection string:

```env
CAREER_CLOUD_PROFILE=azure
CAREER_OBJECT_STORAGE_BACKEND=azure_blob
CAREER_AZURE_STORAGE_CONTAINER=product-data
CAREER_AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=https;AccountName=product;AccountKey=...;EndpointSuffix=core.windows.net
CAREER_AZURE_STORAGE_PREFIX=prod/
```

Account-key alternative (no connection string):

```env
CAREER_CLOUD_PROFILE=azure
CAREER_OBJECT_STORAGE_BACKEND=azure_blob
CAREER_AZURE_STORAGE_CONTAINER=product-data
CAREER_AZURE_STORAGE_ACCOUNT_URL=https://product.blob.core.windows.net
CAREER_AZURE_STORAGE_ACCOUNT_NAME=product
CAREER_AZURE_STORAGE_CREDENTIAL=<account-key>
CAREER_AZURE_STORAGE_PREFIX=prod/
```

A SAS token works for access but cannot presign (downloads stream); a
connection string or account key can presign. Account keys and SAS
tokens in env are secrets; prefer managed identity. Enable Azure soft
delete and versioning.

```env
CAREER_CLOUD_PROFILE=azure
CAREER_OBJECT_STORAGE_BACKEND=s3
```

An explicit `s3` backend is allowed under the `azure` profile; use this

requires SSE `AES256`/`aws:kms`; if the gateway rejects SSE, use the
self-host S3-compatible block above (no cloud profile,
`CAREER_OBJECT_STORAGE_REQUIRED=true`, `SSE=none`).

## Migration (local → object storage)

1. Provision the bucket/container, prefix and least-privilege identity.
2. **Keep the running app on `local`; run the migration process with the
   target backend.** The app service stays `CAREER_OBJECT_STORAGE_BACKEND=local`
   until the flip, but the one-shot migration command is started with
   `CAREER_OBJECT_STORAGE_BACKEND=s3` or `azure_blob` (and that process's
   bucket/container/prefix/credential variables). `migrate-objects
   --dry-run` prints the resolved backend and bucket/container and lists
   local files, keys, unreadable/missing files and collisions. It never
   stages bytes into a local root for later import: bytes go directly to the
   bucket/container the app will use.
3. **Quiesce writes** (maintenance window) or run dual-write. Copying while
   users upload can miss files that arrive after the enumeration.
4. Run `migrate-objects --apply` (idempotent, key-addressed, resumable
   through a migration manifest). It writes each object and verifies size
   and sha256. A manifest is bound to one host, source root and target
   (backend/bucket/prefix/endpoint); a different target is refused until
   the operator passes `--rebind`, which resets transferred entries to
   `pending` and requires a fresh `--apply`/`--verify`.
5. Re-run `--apply` until the delta is **zero**, then run
   `migrate-objects --verify`, which re-reads each object and compares the
   digest (and re-hashes any source that still exists). Any `missing`,
   `unreadable`, `collision` or `failed` entry is **blocking**: the command
   exits non-zero even when other objects verified. Only entries reported
   as `skipped` (no stable owner key, regenerable) are allowed.
6. Backfill the database **before** the flip: `migrate-objects
   --backfill-db` replaces absolute paths with keys and scrubs paths stored
   inside JSON. A dual-read helper (key first, then the legacy path under
   the mounted root) covers the transition. The legacy branch works only
   while the old volume is mounted. The command refuses to run unless
   `--verify` is clean.
7. Flip `CAREER_OBJECT_STORAGE_BACKEND` to `s3` or `azure_blob` and drop the
   migration-only overrides from the app service.
   - **Self-host:** keep the local root read-only for one release. A
     rollback release against that volume must boot with `probe=False`
     (the local health probe writes a `.health` file and would fail on a
     read-only mount).
   - **Cloud:** there is no legacy uploads volume, so the flip is final
     once `--verify` and the backfill are clean.
8. Remove the read-only volume after a clean release and a spot check.

An empty, newly provisioned bucket/container is ready to use without
migration; existing local data needs the `migrate-objects` tool. Never
rewrite objects in place.

**Memory and limits.** The contract's `put` takes bytes, so the tool reads
one whole object at a time. Keep every object under the configured
`CAREER_OBJECT_STORAGE_MAX_MB` / host ceiling; an entry over the cap fails
with a clear error instead of exhausting memory. On workers, budget temp
space and memory for one object per concurrent process.

## Migrate objects (runbook)

`backend/scripts/migrate_objects.py` copies the pre-contract upload tree into
the configured store and then backfills the database. The mapping is
database-driven because ownership lives in the row:

| Legacy location | Object key |
|---|---|
| `<upload_dir>/<document-id><ext>` | `tenants/<user>/documents/<id><ext>` |
| `<upload_dir>/derived/<document-id>/page-<n>.png` | `tenants/<user>/cv_pages/<id>-p<n>.png` |
| `<upload_dir>/exports/career-assistant-export-<job-id>.zip` | `tenants/<user>/exports/<job-id>.zip` |

An export is mapped only when the `background_jobs` row still exists (its
`user_id` supplies the tenant prefix); otherwise it is reported as skipped and
regenerable instead of guessed.

The running **app service stays on `CAREER_OBJECT_STORAGE_BACKEND=local`**, but
the **migration process runs with the target backend** (`s3` or `azure_blob`)
and that process's `CAREER_S3_*`/`CAREER_AZURE_STORAGE_*` values. `--dry-run`
prints the resolved backend and bucket/container. Never stage bytes into a
local root and then point the app at an empty bucket; copy directly to the
target the app will use.

```bash
cd backend

# 1. Plan: reports files, keys, missing/unreadable files and collisions.
python scripts/migrate_objects.py --dry-run

# 2. Copy; idempotent, resumable, manifest saved after every entry.
python scripts/migrate_objects.py --apply
python scripts/migrate_objects.py --apply      # re-run until the delta is zero

# 3. Re-read every object and compare size + sha256. Any blocking entry
#    (missing/unreadable/collision/failed) makes this exit 1.
python scripts/migrate_objects.py --verify

# 4. Backfill the database only after a clean verify.
python scripts/migrate_objects.py --backfill-db

# 5. Flip the app to the object backend.
```

`--backfill-db` sets `documents.object_key`, rewrites only legacy
`uploads/derived/...` page paths to a **verified** `tenants/...` key, and
replaces a legacy `export_path` in the job result with `export_key`. A page
value that is already an object key is preserved; a legacy page with no
verified object is left in place and reported as unmigrated (never nulled).
Alembic revision `0015` is **DDL-only** (it adds the nullable column/index);
the data rewrite above is exclusively this CLI step, so a schema upgrade never
claims an object exists before it does. The backfill is idempotent and refuses
to run without a clean `--verify`. Until it runs, the facade's
dual-read branch serves rows by key first and falls back to the legacy file;
after it runs the object-first path is the normal path. The legacy branch only
works while the old volume is mounted.

The manifest defaults to
`<data_dir>/migrations/object-storage-manifest.json` (`--manifest PATH`
overrides it). It holds each source path relative to the upload root, key,
size, sha256, status, error and the **redacted target** (backend,
bucket/container, prefix, endpoint host — no credentials), plus the host and
source root. It is written atomically (directory fsync included). A different
target, host or source root is refused; `--rebind` adopts the current target
and resets transferred entries to `pending`, requiring a fresh
`--apply`/`--verify`. A corrupt manifest aborts the run; `--force` starts a
fresh ledger. `--force` is also required when the target prefix already
contains objects the manifest does not own; dry-run only warns. Equal or
nested source/target roots are refused. Output never includes an absolute
source path, and one whole object is read per `put` (keep it under the cap).

Rollback (self-host): keep the old uploads volume for one release and flip
`CAREER_OBJECT_STORAGE_BACKEND` back to `local`; a read-only rollback volume
needs a boot with the local health probe disabled (`probe=False`). A cloud
profile has no legacy volume, so its flip is final after `--verify` and the
backfill are clean. **Desktop never runs this tool.**

## Deployment profiles (AWS / Azure)

The cloud overlay requires **both** the profile and the backend, so a
deployment cannot start on an empty interpolation default that silently
means `local`:

```bash
# AWS
CAREER_CLOUD_PROFILE=aws CAREER_OBJECT_STORAGE_BACKEND=s3 \
docker compose -f docker/docker-compose.prod.yml \
               -f docker/docker-compose.cloud.yml up -d

# Azure
CAREER_CLOUD_PROFILE=azure CAREER_OBJECT_STORAGE_BACKEND=azure_blob \
docker compose -f docker/docker-compose.prod.yml \
               -f docker/docker-compose.cloud.yml up -d
```

Provider values live in `docker/.env`. The overlay resets the app's volumes:
the container is stateless for document bytes, including CV page images and
export archives. The `backup` sidecar is database-only in every shape.

**AWS.** Private, TLS-only bucket with Block Public Access on, versioning
on, and a `prod/` prefix (`CAREER_S3_PREFIX=prod/`). Prefer an
instance/task role over static keys; the role needs `s3:ListBucket` on the
bucket (scoped to the prefix with an `s3:prefix` condition) and
`s3:GetObject`/`s3:PutObject`/`s3:DeleteObject` on
`arn:aws:s3:::<bucket>/<prefix>*`. A customer-managed KMS key
(`CAREER_S3_SSE=aws:kms`, `CAREER_S3_KMS_KEY_ID=…`) also needs
`kms:GenerateDataKey` and `kms:Decrypt`. Static keys use the same policy;
rotate them and never commit them. The default is SSE `AES256`; under a
cloud profile `SSE=none` is a boot error.

**Azure.** One private container with soft delete and versioning. Assign
the managed/workload identity **Storage Blob Data Contributor** on the
container scope and set
`CAREER_AZURE_STORAGE_CREDENTIAL=managed_identity`. A managed identity
cannot presign, so downloads stream through the app. A connection string or
account key is the fallback (and can presign); treat both as secrets. Keep
`CAREER_AZURE_STORAGE_PREFIX=prod/` per environment.

## Boot health and observability

Boot builds and probes the store before serving: a missing bucket/container,
one-sided static credentials, a non-HTTPS cloud endpoint or `SSE=none`
raises a `StorageConfigError` and stops the process. The successful boot
logs one redacted line:

```
object storage: backend=s3 bucket/container=<bucket> prefix=prod sse=AES256
```

No access key, secret, session token or endpoint URL is logged.

`GET /health` reports the storage row:

```json
{
  "status": "ok",
  "app": "Career Assistant",
  "version": "0.9.0",
  "storage": {"backend": "s3", "status": "ok", "required": true}
}
```

- The probe is cached for 30 s, so the compose healthcheck (every 30 s)
  does not hammer the provider.
- The provider call is bounded to about 5 s (a daemon thread + join), so a
  slow SDK timeout cannot outlive the container healthcheck; a timeout is
  reported like a transient provider error (degraded, or 503 when storage
  is required). Only contract errors and `OSError` count as storage state;
  an unexpected exception surfaces as a 500 instead of a fake outage.
- A transient provider failure **degrades open**: HTTP 200 with
  `status: degraded` and `storage.status: degraded`.
- HTTP 503 (`status: unhealthy`, `storage.status: unavailable`) only when
  storage is required (a cloud profile or
  `CAREER_OBJECT_STORAGE_REQUIRED=true`) or the failure has been sustained
  for 300 s. A missing target is the boot error above, not a runtime 404.
- `detail` carries the contract error class name only.

## Processors

CV extraction keeps the source bytes untouched and stores derived page
images as their own objects. `process_cv_document` reads the source through
the store, rasterizes text-less pages into a private temp directory (PDF via
`pypdfium2`), uploads each PNG with `put_page`, and runs OCR on the temp
copies; the temp directory is removed on every exit path. The stored
`documents.extraction` payload carries page *keys* (`pages[].image_path`) or
null — never a local path — and `DocumentOut` scrubs any unmigrated value.

| Layer | Store use |
|---|---|
| `/api/v1/documents` upload | `DocumentService.create_upload` → `aput_document` |
| university parse | `DocumentService.extract_text` → `aread` |
| CV pipeline | source `aread`, pages `put_page`, `read_page` on the route |
| document download / page image | `astream` / `aread_page` (no `FileResponse` path) |
| profile photo (data URI, gallery delete) | `aread` / `adelete` |
| user data export | `aread` per document, ZIP uploaded with `put_export` |
| account/profile delete | `adelete` before the row cascade |

Downloads send `Content-Disposition: attachment`, `Cache-Control: no-store`
and `X-Content-Type-Options: nosniff`; page images are the only inline
response and are still `no-store` + `nosniff`.

## Exports and backups

Data-export archives are objects (`tenants/<user>/exports/<job-id>.zip`); the
`/api/v1/background-jobs/{id}/download` route streams them. The job result
carries `export_key`, not a path. Archives past the retention window are
purged from the store at boot.

An export bundles every document a user owns, so it is bounded by its own
ceiling, **not** the 25 MB per-upload cap: `CAREER_EXPORT_MAX_MB` (1–1024,
default **1024**, the contract hard maximum). The archive is spooled to a
temp file and checked against that ceiling before it is written to the
store; an oversized export fails with a message naming the setting (the job
records the error and the HTTP edge maps it to 413). Lower the ceiling only
to bound disk/temp-space use, not to mirror `CAREER_MAX_UPLOAD_MB`.

Local backup/restore (`python -m careerassistant backup|restore`) archives
the SQLite database, the uploads tree and the instance keys. It is a
**desktop/self-host feature** and fails closed (`UnsupportedOperation`) under
an object backend: document bytes live in the provider and provider
durability/versioning is the backup. The compose `backup` sidecar dumps
PostgreSQL only in every shape; there is no uploads tar to disable under a
cloud profile. The datastore quarantine keeps the database and backups in a
cloud deployment and skips the (non-authoritative) local uploads tree.
